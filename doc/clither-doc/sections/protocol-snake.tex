\subsection{Snakes}

If another player is in  proximity  of  the  client,  the server begins sending
information of that player's snake to the client.

The snake's ring-buffer of bezier knots  is  split  up  into  multiple packets.
\verb$MSG_BEZIER$  is sent whenever new knots are appended  or  old  knots  are
removed on the server side. This happens naturally as the snake moves forwards.
This message contains the ``read'' and ``write'' pointers of  the  ring buffer.
The  client  can   use   this   to   resize   its   ring-buffer  appropriately.

Each bezier knot is sent separately via the \verb$MSG_KNOT$ message. The client
must acknowledge each knot with \verb$MSG_KNOT_ACK$. The server keeps track  of
which  knots  have  not  been  acknowledged and will resend them  periodically.

When  the  snake goes out of range of the client, the server will stop  sending
updates to the client and send \verb$MSG_SNAKE_DESTROY$ (must be acknowledged).
If the snake comes  into  proximity  again,  the  server will always assume the
client has destroyed the snake and send everything again.

Parallel  to  snake  creation,  the server will send \verb$MSG_SNAKE_HEAD$  and
\verb$MSG_SNAKE_PARAM$ updates whenever the snake moves forwards. These packets
are  lossy  and  the  client  only  needs  the  most recent head position/snake
parameters. The snake  parameters  contain status effects as well as the length
of the snake, which allows the  client  to  remove  stale bezier knots from the
tail end of the snake.
