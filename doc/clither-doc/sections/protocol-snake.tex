\subsection{Snakes}

If another player is in  proximity  of  the  client,  the server begins sending
information of that player's snake to the client.

The  bezier  curve  can  become quite large. Each knot is sent separately  with
\verb$MSG_KNOT$. These can arrive out of order,  and  are  resent periodically.
The client  collects  the  knots and stores them into a ring-buffer. The server
keeps track of which knots have been acknowledged with \verb$MSG_KNOT_ACK$, and
sends  \verb$MSG_BEZIER$ in response. This message contains the read and  write
pointers of the ring-buffer. This protocol ensures that the  client's  read and
write  pointers  will  always  span  a  range  of  valid,   initialized  knots.

Parallel  to  snake  creation, the server will send some snake metadata such as
\verb$MSG_SNAKE_USERNAME$ which needs to be acknowledged by the client.

\verb$MSG_BEZIER$ is also sent every network  tick  to  update the snake's head
position. This  message  contains  the position of the head knot as well as the
handle of the second knot  (because  it,  too,  changes  as  the  snake moves).

\verb$MSG_SNAKE_PARAM$ is sent whenever the parameters  change.  These  contain
status effects and the length of the  snake.

These messages  are  lossy  and  the  client  only  needs  the most recent head
position/snake parameters.

When  the  snake goes out of range of the client, the server will stop  sending
updates to the client and send \verb$MSG_SNAKE_DESTROY$ (must be acknowledged).
If the snake comes  into  proximity  again,  the  server will always assume the
client has destroyed the snake and send everything again.
